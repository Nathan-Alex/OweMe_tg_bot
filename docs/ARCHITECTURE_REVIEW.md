# Архитектурные комментарии

Этот документ содержит общие моменты для рефакторинга.

## 1. Определить основной способ запуска бота

Сейчас проект поддерживает два способа получения обновлений от Telegram:

- long polling через постоянно запущенный процесс;
- webhook через HTTP-приложение, развёрнутое на Vercel.

Поддержка двух режимов увеличивает количество точек входа, настроек и сценариев развёртывания. В нашем случае, при деплое на сервер или в Railway. достаточно long polling. Т.е. HTTP-сервер и webhook-инфраструктура не нужны.

Как тогда можно изменить логику работы сервиса.

```
Telegram
    │
    │ long polling
    ▼
┌───────────────────────────────┐
│ main.py                       │
│ Запуск и завершение процесса  │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ aiogram Dispatcher            │
│ Маршрутизация обновлений      │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ Handlers                      │
│                               │
│ common.py     — меню, /start  │
│ payments.py   — создание долга│
│ balances.py   — баланс        │
│ settlement.py — закрытие долга│
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ DebtService                   │
│ Бизнес-сценарии и транзакции  │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ PostgreSQL access             │
│ SQL и пул соединений          │
└───────────────┬───────────────┘
                ▼
           PostgreSQL
```

## 2. Разделить большие модули по ответственности

Основная логика сейчас сосредоточена в `handlers/simple.py` и `db.py`. Их нужно разбить по пользовательским сценариям и ответственности.

Возможная структура обработчиков:

```text
bot/handlers/
├── common.py          # /start, главное меню, неизвестный текст
├── payments.py        # Создание и подтверждение запроса долга
├── balances.py        # Просмотр балансов
├── settlements.py     # Закрытие баланса
└── routers.py         # Подключение всех router
```

Клавиатуры, парсинг и форматирование лучше вынести из обработчиков:

```text
bot/keyboards/         # Telegram-клавиатуры
bot/utils/money.py     # Парсинг и нормализация сумм и валют
bot/utils/formatting.py# Форматирование сообщений
bot/utils/links.py     # Deep link и share URL
```

Доступ к данным можно разделить по предметным областям:

```text
bot/db/
├── connection.py       # Пул и жизненный цикл соединений
├── profiles.py         # Работа с профилями
├── payment_requests.py # Запросы на подтверждение долга
├── balances.py         # Чтение и закрытие балансов
└── transactions.py     # Дружба и транзакции
```

Сложные операции нельзя механически разрывать между модулями. Например, подтверждение долга изменяет запрос, дружбу, транзакцию и баланс. Такой сценарий должен выполняться атомарно и координироваться через `DebtService`.

Направление зависимостей:

```text
Telegram handler -> DebtService -> DB modules -> PostgreSQL
```

Handler отвечает за Telegram-ввод и ответ пользователю. Service содержит бизнес-сценарии. DB-модули выполняют SQL и не зависят от объектов aiogram.

Класс следует создавать, когда несколько связанных операций используют общее состояние или зависимости. Для отдельных SQL-запросов без состояния достаточно обычных функций.
